# interview-kit

- Don't overcomplicate. Fewest files and lines that do the job. No framework. Light/dark comes from browser system-color tokens (Canvas, CanvasText, LinkText, AccentColor) following color-scheme; only the warn color is a light-dark() pair. Other theming goes in the theme layer.
- Red-green for every feature or fix: write one test per acceptance criterion, run `npm test` and see it fail, then make it pass. Basic, not deep: test the ACs through public functions, with literal expected values.
- Componentize as UI coalesces: once the same bit of markup shows up in a second place (a question link, a muted note, a pager), pull it into its own small function in `src/components/` and reuse it. Don't extract ahead of the second use.
- CSS layers, in order: `reset, tokens, base, layout, components, utilities, theme` (declared in `src/style.css`). Component CSS lives next to its JS in `@layer components`; layouts in `@layer layout`; `theme` is for a brand theme.
- Every color and size comes from a token in `@layer tokens`; no raw colors elsewhere. Literal `ch` measures, `0`, percentages and `100dvh` are the only exceptions; `test/pack/css.test.js` checks colors, sizes and that each folder's CSS sits in its own layer.
- The default theme stays generic. A new feature or style must look finished with no brand theme loaded: system-color tokens, the system font, plain controls, and no company colors, fonts, logos or button shapes. Brand styling goes only in the pack's `theme/` folder, scoped under `[data-theme="brand"]`, never in `src/`. Before touching a brand theme, read that pack's `AGENTS.md`.
- Never a thick colored stripe down one side (`border-left` / `border-inline-start`) of a card, callout, toast or row, rounded or not; use a full border color, a tint, a badge or a dot. `test/pack/css.test.js` fails on side borders over 1px.
- Outside `reset` and `base`, selectors are class-based: no element or ID selectors. `test/pack/css.test.js` enforces all three, plus no word of the pack's theme name in code, README, AGENTS.md or package.json (docs/ is not checked).
- A user-facing change adds a plain-words bullet to `CHANGELOG.md` under the current version (newest first; bump `package.json` "version" for a new release). A test checks the top CHANGELOG version equals package.json's.
- Content lives in the pack, the folder in `KIT_PACK` (`examples/sample-pack/` by default, format 2). Content changes need no new test; `test/pack/pack.test.js` loads any pack and fails on its errors. Keep `examples/sample-pack/` generic.
- Levels, roles and decisions are pack data. The app names no level and computes no score; `test/judges.test.js` fails on a level name in `src` or `bin`.
- A pack repo runs the app through `bin/interview-kit.js`, which starts Vite or Vitest with the app folder as the working directory and `KIT_PACK` set to the pack's absolute path. Keep that contract: app files resolve from the working directory, pack files from `KIT_PACK`. `test/pack/` is what a pack repo runs, from an installed copy with no `.git` and hoisted dependencies.
- Before reporting done: `npm test` and `npm run build` both pass.
- Git: commit each finished feature on its own (one feature per commit, plain message) once tests and build pass, so any feature can be reverted. `.githooks/` (wired up by `npm install`) rejects a non-noreply author email and a `feat:`-style prefix. The remote is public; never commit a private pack, real questions or candidate data here. Owner subagents commit only, the lead session pushes.
- Subagents: keep one owner per area (UI owns `src/` and `test/`, content owns the pack) and leave them open. Send follow-ups to the existing owner with SendMessage instead of spawning a fresh agent, so it keeps its context and saves tokens.
